# Основы проектирования системы

## Функциональные требования

- публикация постов из путешествий:
  - фотографии
  - короткое описание
  - привязка к месту путешествия
- оценка и комментарии постов других путешественников
- подписка на других путешественников
- просмотр активности пользователей, на которых подписан
- поиск популярных мест для путешествий (наибольшее количество оценок)
- просмотр постов по конкретному месту
- просмотр ленты:
  - общая лента пользователей
  - лента подписок (reverse chronological order)
- доступ через:
  - мобильные устройства
  - браузер

# Привязка поста к локации

Источник истины — координаты, а не справочник мест. У поста всегда хранятся `coordinates` (геометка снимка или точка, выбранная руками) и `geohash` для индексного поиска по префиксу. `location_id` — необязательная ссылка на известное место, а не обязательный внешний ключ.

Матчинг при публикации: по `geohash` берём кандидатов из `locations`, затем по GiST-индексу выбираем ближайшую точку и сравниваем расстояние с `match_radius_m` этого места (у города радиус десятки километров, у конкретного водопада — сотни метров).

- попали в радиус известного места → проставляем `location_id`;
- не попали (фото на шоссе, в поле, в море) → `location_id` остаётся `NULL`, пост никуда не теряется: он находится по `coordinates` и `geohash`, а подпись пользователя сохраняется в `location_title`.

Поэтому «посты по конкретному месту» работают двумя разными запросами: по `location_id` для мест из справочника и по bounding box / `geohash`-префиксу для произвольной точки на карте. В агрегате популярных мест участвуют только посты с непустым `location_id` — точка на трассе сама по себе местом для путешествий не является.

### Выбор: SSD NVMe

Считаем не по количеству дисков, а по латентности. Требуемый IOPS можно набрать и на HDD (59 дисков в массиве), но чтение ленты — это случайные обращения по индексам, где HDD даёт ~10 ms на seek. При SLA прогрузки ленты P95 2.0s и 10 постах в запросе бюджет уходит целиком на диск. NVMe даёт ~0.1 ms и закрывает нагрузку одним диском с запасом на пики.

## MEDIA (картинки постов и комментариев)

Storage = 532 TB/year
Профиль нагрузки: запись один раз, чтение последовательное целым файлом, случайного доступа внутри файла нет.

HDD
Capacity: 532 TB / 32 TB = 17 disks

### Выбор: HDD

Единственная группа, где HDD правильный выбор. Картинки не лежат в СУБД — они в объектном хранилище, отдаются через CDN, и IOPS для них не является ограничением: один файл читается одним последовательным запросом. Ограничение здесь только capacity, а по цене за терабайт HDD дешевле NVMe примерно на порядок. Класть 532 TB/год на NVMe — это платить за латентность, которой всё равно не видно за CDN.

Репликация ×3 (мастер + 2 реплики) следует из требования доступности 99.999%: одиночный диск на группу означает единую точку отказа, при которой пять минут простоя в год недостижимы.

HDD под метаданные не берём нигде: 92 диска против 3 при том, что упираемся не в объём, а в задержку случайного доступа. SATA SSD остаётся как бюджетная альтернатива (11 дисков), но выигрыш в цене не оправдывает трёхкратного роста парка и риска не уложиться в SLA на пиках.
